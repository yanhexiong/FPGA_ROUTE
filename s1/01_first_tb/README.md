# S1-01 第一个 testbench：装好仿真工具，跑通一次「写电路 → 仿真 → 看波形」

## 这一步在干什么

硬件出了错很难在板子上查原因，所以每个电路都要先在电脑上仿真，确认没问题再上板。仿真需要三样东西：

| 东西 | 作用 | 软件里的类比 |
|---|---|---|
| 被测电路（DUT），这里是 `counter.v` | 你要验证的设计 | 被测函数 |
| testbench，这里是 `tb_counter.v` | 产生时钟、给输入、和参考答案比对、导出波形 | pytest 测试文件 |
| 仿真器 Icarus Verilog + 波形查看器 GTKWave | 运行 testbench；把每个信号随时间的变化画出来 | Python 解释器 + 调试器 |

testbench 本身也是 Verilog，但它没有输入输出端口，只在仿真器里运行，不会变成电路。所以里面可以用 `#5` 延时、`$display` 打印这些只有仿真才支持的语法。

## 步骤

1. 安装工具（Ubuntu），装完后运行 `iverilog -V`，能看到版本号即可：
   ```bash
   sudo apt install iverilog gtkwave
   ```
2. 进入本目录，运行仿真：
   ```bash
   make            # 等价于下面两条
   # iverilog -g2012 -Wall -o sim counter.v tb_counter.v   编译
   # vvp sim                                                运行
   ```
   终端应该打印 `PASS：计数、回绕、保持都正确`。
3. 打开波形：`make wave`（或 `gtkwave wave.vcd`）。
   - 左上 SST 面板里展开 `tb_counter`，点 `dut`。
   - 左下会列出 `clk`、`rst`、`en`、`q[3:0]`，全选后点 **Append**。
   - 点放大镜图标「Zoom Fit」看全部波形。
   - 右键 `q` → Data Format → Decimal，用十进制显示。
4. 对照波形读懂 testbench：找到复位结束的那一拍、q 从 15 回到 0 的那一拍、en 变成 0 后 q 保持不动的那一段。
5. 故意改错（手动体验一次，看 testbench 怎么报错）：把 `counter.v` 里的 `q + 4'd1` 改成 `q + 4'd2`，再运行 `make`。testbench 会打印一串 FAIL 和出错时间，到波形里找到那个时刻。改回来。

## 做完的标志

- `make` 打印 PASS，GTKWave 里能看到计数波形。
- 能说清 testbench 里六段代码各自做什么：实例化、时钟、导出波形、复位、逐拍比对、检查保持。
- 自己动手加一项检查：计数到一半时把 `rst` 拉高一拍，检查 q 回到 0，并让参考答案 `golden` 跟着清零。这一步自己写，不要交给 AI。
- 运行 `make check`，3 项全部通过：正确的计数器 PASS，变异体 M1、M2 都 FAIL。

## 检验自己加的检查：`make check`

一项检查写对了，要同时满足两条：

- **不误报**：电路正确时，它不报错。
- **不漏报**：电路有错时，它能报错。

只看 `make` 打印 PASS，只能说明第一条，因为一项什么都没检查的代码也会 PASS。

**分工：你只改 `tb_counter.v`，加上那一项复位检查；`counter.v` 和 `mutants/` 都不用动。** 运行 `make check` 后，它会自动把被测电路依次换成下表 3 个版本，每个版本跑一遍你的同一份 testbench，一次打印 3 项结果：

| 项 | 自动换上的被测电路 | 你的 testbench 应有结果 | 检验的是 |
|---|---|---|---|
| 1 | 正确的计数器 `counter.v` | PASS | 不误报 |
| 2 | 变异体 M1（复位优先级低于使能）`mutants/M1_rst_after_en.v` | FAIL | 不漏报 |
| 3 | 变异体 M2（复位只生效一次）`mutants/M2_rst_once.v` | FAIL | 不漏报 |

变异体（mutant）是故意写错的被测电路，每次只引入一处错误。两个变异体的错误都在复位上，原来的 testbench 都发现不了：

| 变异体 | 错误写法 | 原 testbench 为什么发现不了 | 规格要求 |
|---|---|---|---|
| M1 复位优先级低于使能 | 先判断 `en`，再判断 `rst`，`en=1` 时拉高 `rst` 不起作用 | 开头复位那一拍 `en=0`，复位照常生效 | `rst` 优先，无论 `en` 是什么，`rst=1` 的下一拍 q 都是 0 |
| M2 复位只生效一次 | 第一次复位之后，再拉高 `rst` 都被忽略 | 只在开头复位一次 | 任何时候拉高 `rst`，下一拍 q 都是 0 |

同一项检查要让 3 项都打 ✓ 才算完成，不是每个变异体各写一项检查。哪一项没过，`make check` 会说明原因：

- **第 1 项没过**：检查本身写错了。常见原因是参考答案 `golden` 没有跟着清零，或者清零的时机差了一拍。运行 `make`，看第一条 FAIL 出在哪一拍。
- **某个变异体没检出**：你的检查没覆盖这种错误。打开对应的文件看错误写法，再对照上表的规格要求，想想检查漏了什么。

`make check` 在临时目录里运行，不会覆盖你的 `sim` 和 `wave.vcd`。这种用变异体检验测试的方法叫变异测试（mutation testing），后面的实验写完检查后也可以这样检验。

## 常见问题

- `make check` 最后一行是 `make: *** [Makefile:15: check] Error 1`：检验没通过时，脚本按惯例返回非零的退出码，make 看到后就会打印这一行，意思是"这一步没通过"，不是工具或程序出了故障。3 项全部通过后，这一行就不会出现。`make` 也一样：testbench 报了 FAIL 之后，仿真照常结束，不会出现这一行，只有编译出错时才会出现。

- `iverilog: command not found`：没装好，或者装在了另一台机器上。
- 波形里信号是红色的 `x`：寄存器还没被复位赋值，属于正常现象。复位之后还是 `x`，说明复位逻辑写错了。
- 为什么检查前要等 `#1`？上升沿那一刻寄存器正在更新，稍等一下再读，才能读到更新后的稳定值。后面所有 testbench 都按「上升沿后等一会儿再采样」的规矩来。
